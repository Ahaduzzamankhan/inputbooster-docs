<Lead>
Updating is a file swap. Match the new jar to the exact Minecraft version,
check the Java runtime, and keep a backup of the last stable jar.
</Lead>

## The update procedure

<Steps>
  <Step title="Close the game completely">
    Not just the world — the whole client. The mod writes its config on
    shutdown, and a jar swap while the game is running corrupts the next save.
  </Step>
  <Step title="Delete the old jar">
    Remove every InputBooster jar from `mods`. Do not keep the old one as a
    backup inside the folder; the client loads every jar it finds.
  </Step>
  <Step title="Copy the new jar in">
    Exactly one jar, matching your loader and Minecraft version. See the
    [jar matrix](/docs/installation/jar-matrix).
  </Step>
  <Step title="Start and read the log">
    The mod logs the schema version it loaded and whether it migrated anything.
  </Step>
  <Step title="Re-check your settings">
    Open the settings screen and confirm the values survived.
  </Step>
</Steps>

## Schema versions

The config carries a `config_version`. The current schema is **306** for all current Minecraft targets.

| Schema | Introduced in | Meaning |
| --- | --- | --- |
| 306 | 4.1.2 (26.x) / 3.1.5 (1.21.x) | Current for all seven targets. |
| 305 | 4.1.0-alpha | Previous schema; upgraded to 306 on load. |
| 303 and earlier | 3.x | Older schema, migrated on load. |

When the mod loads a file with a lower version, it logs a migration line and
renames three legacy keys:

| Old key | New key |
| --- | --- |
| `auto_sprint_key` | `auto_sprint` |
| `watap` | `wtap_assist` |
| `pollrate` | `poll_rate_hz` |

<Callout variant="info" title="Migration never invents values">
The migration only renames keys. Every key you did not set keeps its default,
and every key that cannot be parsed is reset to its default and named in a
single warning line. See [validation](/docs/configuration/validation).
</Callout>

## What is preserved across an update

Your config file is read on launch and written on shutdown. A version change
does not touch it unless the schema version changed.

**Preserved:** every key present in your file, as long as it parses and stays
inside its range.

**Reset to defaults:** keys that were missing from the file, keys with an
unparsable value, and keys whose value falls outside the allowed range.

**Not applicable:** the old custom window's size and position are no longer part
of the current settings UI.

<Callout variant="warning" title="A new key looks like a reset">
New settings added in 4.1.x or 4.1.2 appear with their documented defaults
when the key is absent from your existing file. The
[configuration reference](/docs/configuration/keys) lists which key belongs to
which version.
</Callout>

## Rolling back

A rollback is the same procedure in reverse: delete the new jar, put the old
one back.

The risk is a config the new version wrote that the old version does not know.
Because the loader starts from the documented defaults and only applies keys
that are present in the file, an unknown key is simply ignored by the older
build. Rolling back does not break the config.

<Callout variant="note" title="Keep one known-good jar outside `mods`">
A jar sitting in your Downloads folder costs nothing and saves a session when
the current beta build misbehaves. Keep `4.0.3-stable` there.
</Callout>

## Downgrading past the schema

If you move from 4.1 back to a 3.x build, the schema version in your file will
be higher than that build understands. Older builds read `config_version` but
do not have a migration path, so they simply use the keys they recognise.
Nothing crashes; the newer keys are ignored.

## After every update

Run through this short list:

- `Ready!` appears in the log.
- The log contains the polling-thread startup line, and the client command `/inputbooster` reports mod/overlay status.
- The engine mode is the one you expect.
- Your poll rate and CPS cap are the values you set.

If the poll rate or cap came back as a default, the file was reset on load.
The reason is in the log line that starts with `Config entries reset to
defaults`. The [log reference](/docs/troubleshooting/log-reference) explains it.
