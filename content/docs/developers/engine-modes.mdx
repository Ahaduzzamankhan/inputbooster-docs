<Lead>
The engine has two input sources and three modes. The mode decides which
source is allowed to dispatch an action; the other source still updates
state.
</Lead>

## The three modes

```java
public enum Mode {
    AUTO("auto"),
    EVENT("event"),
    POLL("poll");
}
```

| Mode | Behaviour |
| --- | --- |
| `AUTO` | Event hooks when they applied and no known input mod is present, otherwise polling |
| `EVENT` | Event hooks only. Falls back to polling when they are unavailable |
| `POLL` | High-rate sampling only. The hooks still update state but never dispatch |

The configured value maps to the mode like this:

| `engine_mode` | Mode |
| --- | --- |
| 0 | `AUTO` |
| 1 | `EVENT` |
| 2 | `POLL` |

## Resolving the mode

`CompatibilityManager.resolveMode()` decides:

```java
public InputEngine.Mode resolveMode() {
    InputEngine.Mode configured = InputEngine.Mode.fromConfig(InputBoosterConfig.getEngineMode());
    if (configured == InputEngine.Mode.EVENT && !eventSourceActive) {
        fallbackReason = "event hooks unavailable";
        return InputEngine.Mode.POLL;
    }
    if (configured == InputEngine.Mode.AUTO) {
        if (!detected.isEmpty() && InputBoosterConfig.isCompatFallback()) {
            fallbackReason = "compatibility fallback: " + String.join(", ", detected);
            return InputEngine.Mode.POLL;
        }
        return eventSourceActive ? InputEngine.Mode.EVENT : InputEngine.Mode.POLL;
    }
    return configured;
}
```

<Callout variant="info" title="The event source is proven, not assumed">
`eventSourceActive` only becomes true after the first keyboard or mouse event
actually arrives. Until then, `EVENT` mode falls back to polling. This is why
the very first press after startup is handled by the poller even in event
mode.
</Callout>

## The mode can change at runtime

The mode is re-resolved in two situations:

| Trigger | Where |
| --- | --- |
| The first event arrives | `InputEngine.onKeyState` calls `resolveMode()` again |
| `engine_mode` changed in the config | The client tick compares the configured value with the last one |

```java
public void onKeyState(int code, boolean down) {
    CompatibilityManager compat = InputBoosterMod.compatibilityManager;
    if (compat != null) {
        boolean firstEvent = !compat.eventSourceActive();
        compat.markEventSourceActive();
        if (firstEvent) {
            eventDriven = true;
            setMode(compat.resolveMode());
        }
    }
    state.setRaw(code, down);
    if (mode == Mode.POLL) return;
    ...
}
```

<Callout variant="note" title="State always updates">
Even in `POLL` mode the event hooks still write to the state store. A mode
switch therefore never starts from a stale picture, and switching is seamless.
</Callout>

## The compatibility fallback

Some mods own input routing. When one of them is present and
`compat_fallback` is on, the engine keeps polling and leaves event handling
alone instead of competing for it.

Detection is a class-path lookup, not a mod-list dependency, so it works the
through Fabric Loader's mod-id lookup:

```java
private static final String[] KNOWN_INPUT_MODS = {
    "controlify", "midnightcontrols", "controllable", "zoomify"
};
```

The scan runs once during initialisation. A class that cannot be loaded simply
means the mod is not installed.

<Callout variant="warning" title="The list is short and fixed">
Four mod IDs are checked with `FabricLoader.isModLoaded`: Controlify,
Midnight Controls, Controllable and Zoomify. Sodium and Iris are rendering
mods and are not in this list. Other input-owning mods are not detected.
</Callout>

## Reading the resolved mode

The General page in Sodium, or the Input engine section of the vanilla screen,
exposes the configured engine mode and compatibility fallback.
The overlay shows the mode in its engine line, and the status line is:

```java
public String statusLine() {
    return "Input: " + mode.label + (eventDriven ? " (event)" : " (poll)");
}
```

`CompatibilityManager.statusLine()` adds the detection result:

```text
Engine: poll | sodium
```

## Turning the fallback off

With `compat_fallback=false`, `AUTO` no longer downgrades to polling when an
input mod is detected. It picks `EVENT` when the hooks are live.

<Callout variant="danger" title="This is a compatibility risk">
The fallback exists because another mod owns the event routing. Turning it off
means InputBooster dispatches from hooks while that mod also dispatches from
hooks, which can produce doubled or missing actions. If you turn it off, test
in a world you do not mind breaking.
</Callout>

## Forcing a mode

| Situation | Setting |
| --- | --- |
| The hooks are not applying and you want the poller | `engine_mode=2` |
| You want to prove the hooks work | `engine_mode=1` after the first event has fired |
| You are not sure | Leave it on `0` |

The mode is not part of a profile, so switching profiles does not change it.
