<Lead>
The engine has two input sources and three modes. The mode decides which
source is allowed to dispatch an action; the other source still updates
state.
</Lead>

## The three modes

~~~java
public enum Mode {
    AUTO("auto"),
    EVENT("event"),
    POLL("poll");
}
~~~

| Mode | Behaviour |
| --- | --- |
| <code>AUTO</code> | Uses event hooks when they are live and no known input mod requires fallback; otherwise polls |
| <code>EVENT</code> | Uses event hooks only. Falls back to polling while the hooks are unavailable |
| <code>POLL</code> | Uses high-rate sampling for dispatch. Event hooks still update state but do not dispatch |

The configured value maps to the mode:

| <code>engine_mode</code> | Mode |
| --- | --- |
| 0 | <code>AUTO</code> |
| 1 | <code>EVENT</code> |
| 2 | <code>POLL</code> |

## Resolving the mode

<code>CompatibilityManager.resolveMode()</code> decides:

~~~java
public InputEngine.Mode resolveMode() {
    InputEngine.Mode configured =
        InputEngine.Mode.fromConfig(InputBoosterConfig.getEngineMode());

    if (configured == InputEngine.Mode.EVENT && !eventSourceActive) {
        fallbackReason = "event hooks unavailable";
        return InputEngine.Mode.POLL;
    }

    if (configured == InputEngine.Mode.AUTO) {
        if (!detected.isEmpty() && InputBoosterConfig.isCompatFallback()) {
            fallbackReason = "compatibility fallback: " + String.join(", ", detected);
            return InputEngine.Mode.POLL;
        }
        return eventSourceActive ? InputEngine.Mode.EVENT : InputEngine.Mode.POLL;
    }

    return configured;
}
~~~

<Callout variant="info" title="The event source is proven, not assumed">
<code>eventSourceActive</code> becomes true only after the first keyboard or
mouse event arrives. The processor marks the source live and re-resolves the
mode before processing that event. In <code>EVENT</code> or <code>AUTO</code>
mode, that first event is processed by the newly selected event path.
</Callout>

## The mode can change at runtime

| Trigger | Where |
| --- | --- |
| The first event arrives | <code>InputEngine.onKeyState</code> marks the event source live and calls <code>resolveMode()</code> again |
| <code>engine_mode</code> changes | The client tick compares the configured value with the last resolved value |

State is updated by event hooks even in <code>POLL</code> mode. That prevents
the engine from switching to a stale state snapshot.

## The compatibility fallback

When <code>AUTO</code> mode sees a known input-routing mod and
<code>compat_fallback=true</code>, it chooses polling so InputBooster does not
compete with that mod's event-driven dispatch.

The current executable implementation checks four Fabric mod IDs:

~~~java
private static final String[] KNOWN_INPUT_MODS = {
    "controlify", "midnightcontrols", "controllable", "zoomify"
};

for (String modId : KNOWN_INPUT_MODS) {
    if (FabricLoader.getInstance().isModLoaded(modId)) {
        detected.add(modId);
    }
}
~~~

- Controlify
- Midnight Controls
- Controllable
- Zoomify

Sodium and Iris are rendering mods and are not in the list. Other input-routing
mods are not automatically detected.

<Callout variant="note" title="Source comment discrepancy">
The JavaDoc above <code>CompatibilityManager.detect()</code> still describes
the older class-path lookup. The executable method now calls
<code>FabricLoader.isModLoaded(modId)</code>; the code, not that stale comment,
defines the current behavior.
</Callout>

## Reading the resolved mode

The General page in Sodium, or the Input engine section of the vanilla screen,
exposes the configured engine mode and compatibility fallback. The overlay
shows the current mode and detected mod IDs in its engine line.

The status line is built as follows:

~~~java
public String statusLine() {
    String mode = InputBoosterMod.inputEngine == null
        ? "starting"
        : InputBoosterMod.inputEngine.mode().label;
    String compat = detected.isEmpty()
        ? "no known input mods"
        : String.join(", ", detected);
    return "Engine: " + mode + " | " + compat;
}
~~~

Example:

~~~text
Engine: poll | no known input mods
~~~

## Turning the fallback off

With <code>compat_fallback=false</code>, <code>AUTO</code> no longer switches
to polling just because one of the four IDs is detected. It selects
<code>EVENT</code> when the event hooks are live.

<Callout variant="danger" title="This is a compatibility risk">
The fallback exists because another mod may own input dispatch. Turning it
off can make two mods react to the same physical input, producing doubled or
missing actions. Test the change in a world where mistakes do not matter.
</Callout>

## Forcing a mode

| Situation | Setting |
| --- | --- |
| Use the poller | <code>engine_mode=2</code> |
| Require the event path after hooks are live | <code>engine_mode=1</code> |
| Let the mod choose | <code>engine_mode=0</code> |

The mode is not part of a profile, so switching profiles does not change it.
